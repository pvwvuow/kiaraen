# معماری Kiaraen — Android + Supabase

> هدف: اپ یادگیری لغات انگلیسی که از روز اول با **هزینه صفر** (Supabase Free + GitHub Actions)
> شروع کند، اما با رشد به ده‌ها و صدها هزار کاربر **بدون بازنویسی** مقیاس‌پذیر بماند.

## ۱. نمای کلی

```
┌──────────────────────────────────────────────────────────────┐
│                     Android App (Kotlin)                      │
│                                                               │
│  UI (Compose, RTL)          ← فقط نمایش                       │
│    │                                                         │
│  Repositories (Facade)      ← قواعد کسب‌وکار و مپینگ           │
│    │                │                                        │
│    ▼                ▼                                        │
│  Room (محلی)        Supabase (_REMOTE_)                      │
│  «منبع حقیقت آفلاین»  Auth (GoTrue) — PostgREST — Storage    │
│    │                │                                        │
│    └──► SyncEngine (WorkManager) ◄──┘                        │
└──────────────────────────────────────────────────────────────┘
                         │
                         ▼
              PostgreSQL + RLS (Supabase)
              content_*  (عمومی، فقط‌خواندنی)
              user_*     (خصوصی، RLS سخت‌گیرانه)
```

اصل طلایی: **اپ آفلاین کامل کار می‌کند.** همه چیز اول در Room نوشته می‌شود؛ سرور بعداً و
فقط برای «همگام‌سازی» درگیر می‌شود. هیچ صفحه‌ای منتظر شبکه نیست.

## ۲. لایه‌ها و مسئولیت‌ها

| لایه | پکیج | مسئولیت | ممنوع |
|---|---|---|---|
| UI | `ui/**` | Compose، حالت صفحه، ناوبری | تماس مستقیم با Room/Supabase |
| Repository | `data/repository/**` | مپینگ DTO↔Entity، قواعد نوشتن | منطق UI |
| Sync | `data/sync/**` | صف، retry، LWW، pull | تصمیم‌های محصول |
| Remote | `data/remote/**` | supabase-kt، DTOها | کش کردن |
| Local | `data/local/**` | Room، DAOها | دانستن «شبکه» |
| Domain | `domain/**` | مدل‌های خالص، SRS، قواعد سینک | هر وابستگی فریم‌ورک |

## ۳. DI

`AppContainer` (تزریق دستی، الگوی توصیه‌شده گوگل برای اپ‌های این اندازه). همه وابستگی‌ها
از طریق constructor تزریق می‌شوند → تست واحد با fake کار می‌کند و مهاجرت به Hilt در
آینده صرفاً مکانیکی است. **اکنون Hilt اضافه نشده** چون پیچیدگی فوری نمی‌خواهد.

## ۴. جریان‌های اصلی

### یادگیری (آفلاین)
`QuizScreen → ProgressRepository.recordReview() → Room (pendingSync=1)`
همان لحظه SRS محلی + review_log رویدادی ثبت می‌شود. UI هرگز منتظر شبکه نمی‌ماند.

### همگام‌سازی (فقط دلتا)
`SyncWorker` (شبکه‌دار، backoff نمایی) → `SyncEngine.syncAll()`:
push رویدادها → push وضعیت → pull وضعیت (LWW) → pull آمار. جزئیات کامل در `04-sync-offline.md`.

### محتوا (یک درخواست کوچک)
بررسی یک ردیف `content_packs` → اگر نسخه جدید بود، پک JSON از Storage دانلود و
اتمیک در Room نصب می‌شود. پک نسخه ۱ همین الان **داخل APK** است (بوت‌استرپ آفلاین).

## ۵. تصمیم‌های معماری و دلیلشان

| تصمیم | چرا |
|---|---|
| تک‌ماژول با لایه‌بندی پکیجی | تیم ۱ نفره؛ مالتی‌ماژول وقتی توجیه داشت (۲+ توسعه‌دهنده / زمان بیلد) اضافه می‌شود |
| Room به‌عنوان «منبع حقیقت محلی» | آفلاین‌فرست واقعی، نه کش ساده |
| رویداد (review_log) جدا از وضعیت (progress) | آمار بی‌نهایت قابل بازسازی؛ جداول تجمیعی فقط «کش»اند |
| client_event_id تولیدشده روی دستگاه | retry امن، بدون دیتای تکراری — مهندسی‌شده در DB نه در اپ |
| SRS-lite حالا، ستون‌های SM-2 کامل از الان | مهاجرت آینده به FSRS/SM-2 بدون ALTER |
| سطح‌بندی در `levels` جدولی | اضافه‌کردن سطح جدید = یک INSERT، نه تغییر کد |
| آزمون تولیدی روی دستگاه | صفر هزینه سرور برای ۵۰۰۰ لغت × N کاربر |
